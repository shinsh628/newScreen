# NewScreen — 노트 캡처 감지기 진행 상황

## 목적
리듬게임 화면을 실시간으로 읽어 osu!로 노트를 실시간 변환·주입하는 큰 프로젝트의 1단계.
"노트 캡처가 실제로 잘 되는가"만 검증하는 최소 테스트 프로그램. (2단계는 6키 osu! 패턴 재현 검증,
이후 실시간 주입.)

## 구성
- `Program.cs` / `ControlPanelForm.cs`: 제어판. 레인 4개 위치 설정, 캡처 시작/중지, 단축키 편집,
  항상 위에 표시, 레인별 실시간 감지 상태 박스.
- `ColumnPickerOverlay.cs`: 반투명 풀스크린 오버레이. 레인 1→4 순서로 4번 클릭해서 각 레인 캡처 x좌표 지정.
  y좌표는 항상 화면 최상단(0)부터 `StripHeight`까지 고정.
- `Settings.cs`: `ColumnXs`(레인 4개 x좌표), 핫키, 항상 위에 표시 옵션을 JSON으로 저장.
- `NoteDetector.cs`: 4레인의 x범위를 통째로 덮는 넓은 영역을 **한 번의 CopyFromScreen 호출로 동시에**
  캡처(레인별로 따로 캡처하지 않음 — 아래 "해결된 문제" 참고). 매 틱(현재 100ms 목표) 캡처해서
  레인별로 잘라 행(row) 단위로 스캔, 상태(0=배경/1=흰·파랑 일반노트/2=빨강 사이드노트) 판정.
  결과를 원본(raw) 로그와 가공(events) 로그 두 파일에 기록.
- `NoteTracker.cs`: 레인마다 독립적으로 여러 틱에 걸쳐 같은 런(run)을 추적해서 노트 하나로 확정.
  - 마디선 필터: `FindRuns()`에서 폭이 `MeasureLineMaxWidthPx`(4px) 이하인 run은 매칭 후보에서
    아예 제외(마디선/장식선 노이즈가 트랙 매칭에 끼어들지 못하게).
  - 인접 run 병합: 남은 run들 사이 배경 간격이 `MaxRunMergeGapPx`(5px) 이하면 하나로 합침
    (안티에일리어싱 등으로 생기는 미세한 끊김 방어).
  - 매칭은 "전역 최소오차 우선"(아래 "해결된 문제" 참고) — 트랙 등록 순서와 무관하게, 이번 틱의
    모든 (트랙,run) 후보 쌍을 오차 기준 정렬해서 가장 잘 맞는 쌍부터 확정.
  - 속도 미확정(샘플 1개) 트랙은 다음 틱 예측에 `AssumedBootstrapVelocityPxPerMs`(1.2px/ms)를 씀
    (v=0 가정 시 100ms 틱에서 실제 이동량이 고정 허용오차를 넘어서 노트가 계속 1틱짜리로 쪼개지던
    문제 해결).
  - `NoteEvent.StartMs`는 원시 틱 타임스탬프가 아니라, 첫/마지막 샘플의 leading-edge 픽셀좌표와
    속도로 "y=0/y=stripHeight를 지난 정확한 순간"을 역산한 값(캡처 주기와 무관하게 정밀).
  - `EndMs`는 필드 자체를 없앰 — 판정선이 스트립보다 훨씬 아래에 있어서 캡처창 통과시간이 섞인
    무의미한 값이었음. 홀드 지속시간은 `LengthPx / VelocityPxPerMs`로 계산.
  - 색상은 런이 살아있는 동안 다수결로 판정: Side가 더 많으면 길이 무관 SIDE로 분류.
- 로그 위치: `screenLog/capture_{시작시각}_raw.log`, `screenLog/capture_{시작시각}_events.log`.
  raw 로그 포맷: `elapsedMs\tlane0\tlane1\tlane2\tlane3`(4레인 동시 캡처라 레인별 타임스탬프 불필요).
  events 로그 포맷: `lane\tstartMs\tvelocity_px_per_ms\tlengthPx\tkind(TAP/HOLD/SIDE)`.

## 현재 캡처 설정
- `StripWidth=6`, `StripHeight=400`(원래 50이었음 — 렉으로 인한 프레임 중복/스킵 영향을 줄이려고
  넓힘), `TickInterval=100ms`(원래 60Hz), `BrightnessThreshold=15`(원래 40 — 배경이 거의 순수
  검정이라 안전하게 낮춤, 얇은 노이즈 blob이 늘어도 매칭 전에 필터링되므로 안전).

## 실기 테스트로 검증된 것
1. 진입(위쪽 클리핑)→정상(양끝 자유)→이탈(아래쪽 클리핑) 3단계 패턴이 이론과 일치.
2. 마디선이 만드는 신호가 실제 노트와 폭으로 구분됨.
3. 프레임 중복/스킵 문제를 예측 기반 매칭 + "실제 변화 시점 기준" 속도 계산으로 해결.
4. 4레인 동시 캡처 시 레인별 독립 추적 정상.
5. 색상 기반 사이드노트 판정 정상. 레인0·1 동시 SIDE=왼쪽, 레인2·3 동시 SIDE=오른쪽
   (osz 변환 시 시작시각 250ms 이내로 짝지어 병합).
6. **100ms/400px로 낮춰도 타이밍 정밀도가 떨어지지 않음** — 위치+속도 기반 역산이라 원리적으로
   캡처 주기가 정밀도의 하한이 아님(단, 아래 알려진 한계의 "SV 강건성" 항목은 예외).

## 이번 세션에서 발견하고 해결한 버그들
1. **TAP 파편화 (100ms 전환 초기)**: 속도 미확정 트랙이 v=0으로 다음 틱을 예측해서, 100ms 틱에서
   실제 이동량(~70px)이 고정 허용오차(15px)를 넘어 매 틱 새 트랙으로 오판 → `AssumedBootstrapVelocityPxPerMs`
   도입으로 해결.
2. **홀드노트가 여러 개로 쪼개져 겹쳐 찍힘**: 400px로 넓히면서 홀드노트 내부의 얇은 장식선/마디선이
   같은 틱에 별도 run으로 잡혀 매칭을 방해 → `FindRuns()`에서 매칭 이전에 얇은 run을 아예 제외하도록
   수정.
3. **레인 간 캡처 시점 스큐**: 4레인을 순서대로(0→1→2→3) 따로 캡처하면서 전부 같은 틱 타임스탬프를
   붙여서, 동시에 등장한 노트인데 레인마다 다른 시각으로 역산되는 문제(최대 수십 ms) →
   4레인 x범위를 통째로 한 번의 CopyFromScreen으로 동시 캡처하도록 변경. 재발 불가능한 방식으로 해결
   (레인별 타임스탬프 보정이 아니라 애초에 스큐가 생길 수 없는 구조로 변경).
4. **StartMs가 틱에 양자화됨**: 위치+속도로 역산하는 로직을 `Finalize()`에 추가 (원래는 raw 틱
   타임스탬프를 그대로 썼음).
5. **EndMs가 무의미한 값이었음**: 판정선이 스트립보다 훨씬 아래에 있어서 "캡처창 통과 시간"만
   반영하는 값이었는데, osz 변환 스크립트가 이걸 그대로 홀드 종료시각으로 써서 모든 롱노트가
   실제보다 ~570ms(스트립 높이/속도)씩 길게 나오는 버그가 있었음 → EndMs 필드 제거,
   홀드 종료시각은 `startMs + lengthPx/velocity`로 계산하도록 수정.
6. **트랙 매칭이 그리디 순서 의존적이었음 (가장 중요한 버그)**: `_active` 리스트 순서대로 트랙마다
   그리디하게 "가까우면 잡고 보는" 방식이라, 폭이 넓은(홀드류) run은 허용오차 판정이 관대해서
   이미 화면 밖으로 거의 빠져나간 낡은 트랙이 실제로는 다른 새 트랙 몫인 run을 가로채는 문제가
   있었음(다른 레인은 동시에 등장/종료하는 홀드인데 특정 레인만 시작·속도가 어긋나거나, 뒤이은
   홀드가 앞 홀드와 시간이 겹쳐 찍힘). → 이번 틱의 모든 (트랙,run) 후보 쌍을 오차 기준으로 정렬해서
   가장 잘 맞는 쌍부터 확정하는 "전역 최소오차 우선" 방식으로 교체. 검증: 겹치는 HOLD/SIDE 클러스터가
   15건→0건.

  하나의 히트오브젝트로 병합.
- TAP/HOLD 판정: `lengthPx >= 90`이면 롱노트(`type=128`+endTime), 아니면 단노트.
- 변환 스크립트는 프로젝트 폴더가 아니라 세션 스크래치패드에 둠(재사용 시 새로 작성 필요 —

## 알려진 한계
- **SV(스크롤 속도) 강건성 미해결**: `NoteTracker`가 노트 하나의 속도를 스트립 통과 전체(~570ms)
  평균으로 계산하는데, 만약 노트의 스트립 통과 도중에 SV 전환 시점이 걸리면 그 노트의 속도가
  전/후가 섞인 값이 됨 → 전환 경계 근처 노트 몇 개(밀도에 따라 2~4개)의 `StartMs` 역산이 부정확해짐.
  실기 캡처(capture_2026-08-21_04-34-37)에서 실제로 SV 구간 두 개를 발견함(96.0~110.0초, 130.9초~
  곡 끝, 둘 다 0.700→~0.726px/ms, 약 +3.6%). 이 세션에서 SV 자체는 이 정도로 약해서 osz 품질에
  체감되는 문제는 없었음. **다음 세션 작업 후보**: `Finalize()`의 역산에 트랙 전체 평균 속도 대신,
  기준점(등장은 첫 샘플, 퇴장은 마지막 샘플)에 가까운 로컬 샘플 몇 개만으로 계산한 로컬 속도를
  쓰도록 변경 — 그 노트가 어느 SV 구간에서 등장/퇴장했는지와 무관하게 그 순간의 진짜 속도를 반영.
  게임 자체의 SV 렌더링은 (거의 모든 스크롤형 리듬게임처럼) 판정선까지의 거리가 아니라 현재
  곡 재생시각 기준으로 화면 전체에 동시 적용되는 것으로 추정 — 즉 캡처 띠 위치가 판정선에서 멀어서
  SV 반영이 지연되는 문제는 아닐 가능성이 높고, 문제는 우리 쪽 "전체 평균 속도" 계산 방식에 있음.
- 개발 노트북이 렉이 있어 raw 로그에 이따금 velocity가 튀는 샘플이 보임(정상 범위, 노트 자체가
  조각나지는 않음 — 위 버그들 해결 후 확인).
- 좌/우 사이드노트 병합은 `NoteTracker` 자체가 아니라 osz 변환 스크립트 단계에서만 이루어짐
  (레인별 SIDE 이벤트는 events.log에 그대로 독립적으로 남음).

# 2단계: 패턴 복제 모드 (2026-08-21 완료)

대상 게임 화면에서 읽은 노트를 **osu!에 실시간으로 주입**하는 것까지 동작한다.
osu! 쪽 구현은 lazerSR에 있다 — `C:\dev\lazerSR\lazerSRClean`, `docs\guides\architecture.md` §19.

## 동작 흐름

1. osu!에서 **편집 → 패턴 복제** 진입 → 노트 없는 6키 빈 맵으로 대기
2. NewScreen에서 **대상 창 선택 → 칼럼/판정선 설정 → 속도 캘리브레이션 → 캡처 시작**
3. 캡처 시작이 곧 **osu! 오버레이 표시 + 노트 전송 시작**
4. 대상 게임에서 곡을 플레이하면 osu!에 같은 패턴이 실시간으로 재현된다

## 1단계에서 바뀐 것 (위 내용 중 무효가 된 부분)

| 항목 | 1단계 | 지금 |
|---|---|---|
| 캡처 방식 | `CopyFromScreen`(데스크톱 합성) | **WGC**(창 직접 캡처, 가려져도 읽힘) |
| 좌표 기준 | 화면 절대좌표 `ColumnXs` | **대상 창 클라이언트 좌표** `ClientColumnXs` |
| 타임스탬프 | `Stopwatch`(요청 시각) | **`frame.SystemRelativeTime`**(합성 시각) |

| 속도 | 노트별 실측 | **세션 전역값**(캘리브레이션) |
| 결과 | raw/events 로그 파일 | **파이프로 osu!에 직접 전송** + raw/events 로그 병행(캘리브레이션 모드 제외) |

## 설계 판단과 근거

### 판정선 기준으로 시각을 옮긴 것
osu!의 `HitObject.StartTime`이 곧 "판정선에서 쳐야 하는 시각"이라, 이 기준으로 맞춰야 두 게임의
타이밍이 일치한다. `hitMs = t0 + judgementLineY / v`.
**노트가 보이기 시작하는 시점이나 스크롤 속도는 양쪽이 달라 보이는 것이 정상이다** — 일치해야 하는 건 판정 시각뿐.

### 속도를 전역값으로 바꾼 것
판정선 기준으로 옮기면 **속도 오차가 판정선까지의 거리만큼 증폭된다**. 실측 로그에서 노트별 속도를
쓴 결과 223건 중 27건(12%)이 50ms 넘게, 최악은 **2.5초**까지 어긋났다(원인은 표본이 1~2개뿐인
노트의 추정 노이즈). 중앙값은 정확히 0.7000이고 90%가 ±5% 안에 있었으므로, 전역값 하나를 쓰면
이 오차가 구조적으로 사라진다. 그래서 **속도만 재는 캘리브레이션 모드**를 따로 만들었다.

동시치기 72개로 잔여 오차를 측정한 결과 **편차 중앙값 0.0ms, 97%가 10ms 이내**였다 —
즉 실측 (시각, 위치) 쌍 자체는 왜곡되지 않았고, 튀던 속도는 추정 노이즈였음이 확인됐다.
(단, 이 검사는 **모든 레인이 함께 밀리는 오차**는 못 잡는다. 대상 게임 렌더 지연이나 판정선 클릭
오차가 그런 성격인데, 전부 고정 오프셋이라 필요해지면 값 하나로 보정하면 된다.)

### 노트를 "처음 감지한 순간" 보내는 것
1단계의 `NoteEvent`는 노트가 스트립을 다 지나간 뒤에야 확정됐다. 그대로 쓰면 리드타임을
통과시간(~570ms)만큼 통째로 잃는다. 그래서 첫 감지 틱에 바로 내보낸다(`LiveNote`).
위 경계가 아직 안 들어와 길이를 모르면 **끝 미정 롱노트**로 먼저 보내고, 나중에 확정되면 잘라낸다.
길이는 `v × (위 경계가 y=0을 지난 시각 − T0)`로 구한다 — **스트립보다 긴 노트에서도 성립한다**.

## 실기로 확인한 함정 (다시 밟지 않도록)

1. **파이프 클라이언트는 `PipeOptions.Asynchronous` 필수.** 없으면 동기 핸들이 되고 Windows가
   같은 핸들의 I/O를 직렬화해서, 수신 스레드가 `ReadFile`에서 대기하는 동안 `WriteFile`이 함께 멈춘다
   — **첫 10바이트 쓰기부터 영구 대기**했다. 정상 동작하던 Launcher의 클라이언트는 이 옵션을 쓰고 있었다.
2. **들어오는 줄을 읽어서 버려야 한다.** osu!는 게임플레이 중 100ms마다 브로드캐스트하는데
   `PipeServer`는 가장 최근 연결 하나에게만 쓴다. 안 읽으면 상대가 막힌다.
3. **`pc:sync`는 매 틱 반복 전송.** 한 번만 보내면 캡처 시작과 osu! 모드 진입의 순서에 의존하게 되고,
   모드 진입 전에 온 것은 버려져 시각 원점이 영영 안 잡힌다.
4. **칼럼 좌표는 찍는 시점에 클라이언트 좌표로 변환해 저장한다.** 캡처 시작 시점에 변환하면
   그 사이 창이 움직였을 때 조용히 어긋난다.
5. 설정 프로퍼티 이름을 값의 의미가 바뀔 때마다 함께 바꿨다(`ColumnXs`→`ClientColumnXs`,
   `StartMs`→`HitMs`). 이름을 유지하면 옛 값을 그대로 읽어 **원인 추적이 매우 어려운 오작동**이 된다.

**진단은 추측보다 계측이 빠르다.** 위 1번을 잡는 데 가설 세 개를 헛짚었고, "어디까지 실행됐는지"를
찍는 로그를 넣고 나서야 한 번에 잡혔다. 증상만 보고 원인을 추론하는 대신 실행 경로를 먼저 찍을 것.

## 배포

- `installer\NewScreen.iss` + `installer\build-installer.ps1` — self-contained publish + Inno Setup
- **AppId `{3401B117-E7C6-4893-95A3-76890D3A21F9}`** — 조상 프로그램 ScreenEditor와 다르다(같으면 서로 덮어씀)
- **`MinVersion=10.0.19041`** — WGC가 Windows 10 2004 이상을 요구한다. 안 막으면 설치는 되고
  캡처 시작에서야 실패해서 원인을 알기 어렵다
- 산출물: `installer\Output\NewScreen-Setup-1.0.0.exe` (약 52MB, .NET 런타임 포함)

## 남은 것 / 알려진 한계

- **SV 강건성 미해결** — 위 1단계 "알려진 한계" 참고. 현재는 SV가 없다고 가정하고 전역 속도를 쓴다.
  SV가 있는 곡에서는 전환 구간 노트의 시각이 어긋난다.
- **글로벌 오프셋 보정 없음** — 대상 게임 렌더 지연·판정선 클릭 오차 같은 고정 오프셋을 보정하는
  수단이 아직 없다. 실제로 쳐보고 "전체가 일관되게 빠르다/느리다"가 느껴지면 슬라이더 하나 추가하면 된다.
- **리드타임 예산 실측 안 함** — 계산상 첫 감지 시점에 900ms 안팎이 남고 실사용에서 문제가 없었지만,
  스크롤이 빠른 곡에서 부족해질 수 있다. 부족하면 늦게 도착한 노트가 조용히 버려진다(강제 미스 방지).
- **오버레이 반투명 시 DWM 썸네일 동작 미확인** — 100% 미만이면 창이 레이어드가 되는데
  그 상태에서 썸네일이 제대로 합성되는지는 확인이 필요하다.

# 개발 이어가기 — 최소 준비물

새 PC(예: 방금 포맷한 Windows 11)에서 이 프로젝트 개발을 이어가려면:

1. **Windows 11** — 빌드 타깃이 `net8.0-windows10.0.22000.0`(WGC 노란 캡처 테두리를 끄는
   `IsBorderRequired`가 22000부터 있음). 실행 최소 요구는 Windows 10 2004(19041)이지만 개발 자체는
   Win11 권장.
2. **.NET 8 SDK** — `winget install Microsoft.DotNet.SDK.8` 또는 공식 인스톨러. (`dotnet --version`으로 확인.)
3. **Windows 10/11 SDK 10.0.22000.0 이상** — `Windows.Graphics.Capture`(WinRT) 프로젝션 참조에 필요.
   Visual Studio 설치 시 ".NET 데스크톱 개발" 워크로드에 포함해서 받거나 단독 SDK 설치.
4. **에디터** — Visual Studio 2022(WinForms 지원) 또는 VS Code + C# 확장. `dotnet build`만으로도 빌드 가능.
5. **NuGet 패키지 복원용 인터넷 연결** — `Vortice.Direct3D11` 등 최초 1회 다운로드 필요(이후 캐시됨).
6. **Inno Setup 6** — 설치 프로그램(.exe) 빌드할 때만 필요. `installer\build-installer.ps1`이
   `C:\Users\shins\AppData\Local\Programs\Inno Setup 6\ISCC.exe` 경로를 하드코딩하므로, 새 PC에서는
   그 경로에 설치하거나 스크립트의 `$iscc` 값을 수정해야 함.
7. **git** — 저장소가 `https://github.com/shinsh628/newScreen.git`에 있으므로 `git clone`으로 받으면 됨.

옵션(있으면 편함, 없어도 이 프로젝트 자체는 빌드/실행 가능):
